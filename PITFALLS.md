- siw deadlocks in ibv_destroy_cq when the queue still holds completions or unacked events (captured with gdb). RDMA_Stream::reset() now drains both queues and acks what is left before destroying them.
- RDMA_Acceptor::accept() returned RDMA_Stream and threw on any non-CONNECT_REQUEST event — but its channel also carries its own connections' disconnects, so one replica hanging up killed the listener. It now returns std::optional, skips those events, and treats "nothing waiting" as nothing waiting.
- io_uring's kSend completion never consumed its span, so the same reply was written forever (7.5 MB of +PONG in 2 s). redis-cli hides this; redis-py saw "Connection has data". The epoll path consumed nothing on a partial send either — both fixed.
- RESP::Receiver cleared its buffer per command, silently dropping everything after the first command in a pipeline, and could not grow for a request larger than 512 bytes. Both fixed; the server's buffers are sized for real pipelines.
- CLIENT SETINFO (redis-py 8 announces itself on connect) is answered, and SAVE is now BGSAVE with Background saving started.
- A capturing lambda that is a coroutine does not copy its captures into the coroutine frame. If its closure is a temporary, a suspended coroutine can later read destroyed capture storage. Prefer named coroutine functions with explicit parameters; when a coroutine lambda is unavoidable, ensure the closure object owns copied captures and outlives the coroutine. See [A capturing lambda can be a coroutine, but you have to save your captures while you still can - The Old New Thing](https://devblogs.microsoft.com/oldnewthing/20211103-00/?p=105870).
- A RESP multi-bulk ends where its last element ends: there is no CRLF after the elements, only inside them. A reader that waits for one waits forever, and the symptom is not a hang but a lag — every command is answered when the *next* command's bytes arrive, so a pipelining client (redis-benchmark -P 64) sees the last reply of each batch never come. Nothing catches this except a client that stops sending at the end; `Application/Server/testing/ScannerTesting.cpp` pins it.
- The RESP decoder consumes the bytes it reads, so once it is half way through a command those bytes are no longer at the front of the receive buffer. A reader that scans the buffer in place must not run while that decoder is holding the rest of a command, or it starts in the middle of one and reads its arguments as commands (`ERR unknown command ''`). `Receiver::take()` scans only when no decoder is pending, and the decoder is dropped the moment a command completes.
- `Buffer::reserve()` copied the bytes it was holding to the front of the new storage but left `begin_`/`end_` where they were, so a buffer that grew while it held unread bytes past the front went on describing the old offsets — memory its bytes had never been copied to. What came out was whatever was there (often a previous allocation's contents, which is why the corruption looked like *earlier* pipeline data rather than noise). Between fixing that and the decoder above, the server answered `ERR unknown command ''` to a `SET`. The offsets now follow the copy; `Foundation/testing/BufferTesting.cpp` is the regression.
- Reading a command in place (words as views into the receive buffer, no `RESP::Object` tree) and writing replies straight into the batch buffer (`RESP::AppendObject`, no piece list, no string per number) took GET from 1.08M to 2.94M/s at 1000 connections on io_uring, at the same ~34% CPU Redis uses for 3.04M/s. Both are one pass and no allocation per command; the object tree and its strings were ~50% of the server's CPU.
